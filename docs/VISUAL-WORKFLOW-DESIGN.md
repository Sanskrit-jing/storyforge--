# FLOW-1（历史实现）/ FLOW-2（重构）· 自由节点创作模式

> 2026-07-26 产品校正：下文 FLOW-1 把 `PromptWorkflow` 增加画布视图的方案，已被作者明确
> 判定为层级与功能均不符合节点模式。FLOW-1 代码只作为迁移来源，不再构成完成证据。
> 正式重构以 [`AUTHORING-PLATFORM-DESIGN.md`](./AUTHORING-PLATFORM-DESIGN.md) 的
> FLOW-2 为准：独立入口、独立数据模型、字段级自由来源、动态端口、逐节点可见输入输出和
> 持久运行记录。

> 状态：第一阶段已交付（2026-07-26）。
> 用户目标：像 ComfyUI 一样，用可拖拽、可连线、可检查的节点图编排 StoryForge 的创作过程，
> 但不复制一套 AI、上下文、写回或 Agent 系统。

## 1. 产品定位

FLOW-1 曾被实现为 StoryForge 的作者可控编排层：把当前线性的 `PromptWorkflow` 升级为
可视化有向无环图（DAG），每个可执行节点仍然落到现有 `GenerationNode`，项目事实仍经
`CONTEXT_SOURCES → assembleContext()` 读取，作品写回仍由作者确认后经
`FIELD_REGISTRY / AdoptionSchema → adopt()` 完成。

```text
作者与可视化画布
        │
        ▼
FLOW-1 图校验 / DAG 编译 / 运行状态
        │
        ├── 手动编排：作者在画布连接节点
        └── 自动编排：未来 AgentRunner 生成或建议同一种图
        │
        ▼
PromptWorkflow step → GenerationNode
        │
        ├── 读：CONTEXT_SOURCES / assembleContext
        ├── 跑：现有模型路由、PromptTemplate、usage logger
        ├── 判：确定性 gate / Canon
        └── 写：作者确认 → adopt
```

这一定义解决层级冲突：

- `GenerationNode` 是最小执行单元。
- `PromptWorkflow` / FLOW-1 是作者明确指定的静态编排。
- `AgentRunner` 是模型动态决定下一步的自动编排。
- `ChatCopilot` 是面向作者的自然语言入口。
- FLOW-1 与 Agent 可以互相转换或复用节点，但不能各自拥有一套执行和写回内核。

## 2. 当前代码事实

- `promptWorkflows` 已是 `PROJECT_TABLES` 登记的全局配置表；用户工作流可保存、克隆、
  删除并单独导入导出。
- `PromptWorkflow.steps` 当前只支持线性顺序，`inputMapping.previousOutput` 只认识紧邻
  上一步。
- `WorkflowRunner` 已提供逐步执行、暂停、跳过、重试、编辑输出和作者点击保存。
- 每个步骤已经通过 `createWorkflowGenerationNode()` 接入 `GenerationNode`。
- `GenerationNode` 默认只运行到候选与 gate，不会自动采纳。

因此第一阶段是**兼容升级现有工作流**，不是新增 `visualWorkflows` 表或第二个 Runner。

## 3. FLOW-1 历史第一阶段范围（已撤销“节点模式完成”结论）

### 3.1 图数据

在 `PromptWorkflow` 中增加可选 `graph`：

```ts
interface PromptWorkflowGraph {
  version: 1
  nodes: Array<{
    stepId: string
    x: number
    y: number
  }>
  edges: Array<{
    edgeId: string
    sourceStepId: string
    targetStepId: string
    targetVariable: string
  }>
  viewport?: { x: number; y: number; zoom: number }
}
```

- 节点业务配置仍唯一存放在 `steps`，图节点只保存布局，不复制 Prompt、参数或写回目标。
- 连线表示“源节点已确认输出 → 目标节点变量”。同一源输出可以分发到多个下游。
- 旧工作流没有 `graph` 时按现有步骤顺序生成兼容布局和必要的线性连接，不迁移、不改写。
- 图数据跟随现有工作流保存、克隆和工作流 JSON 导入导出；它不是项目手稿，不进入项目
  便携备份，也不参与项目/世界删除。

### 3.2 确定性图编译

执行前必须由纯代码校验：

- `stepId` 唯一，图节点必须引用现有步骤。
- 连线两端必须存在，禁止自环、重复边和空变量名。
- 禁止有向环；使用稳定拓扑排序，顺序相同时沿用 `steps` 的作者顺序。
- v1 允许分叉与汇合，但仍按拓扑顺序逐个执行，不并发调用模型。
- 目标节点只读取自己的入边产物；无边节点只读取登记项目上下文和作者输入。
- 运行开始后冻结图快照；编辑图会使旧运行候选失效，不跨图确认或写回。
- 重新生成或编辑较早节点后，后序候选全部作废并按拓扑顺序重跑，不能保存基于旧输入的
  下游结果。

### 3.3 可视化画布

- 在工作区提供独立“节点模式”入口，但复用同一个 `PromptWorkflowsPanel` 和
  `promptWorkflows` Store。
- 用户工作流可以在画布中新增、删除和拖动节点。
- 节点提供输入/输出端口；作者通过“选择源端口 → 选择目标端口”建立连接。
- 右侧检查器编辑节点名、Prompt 模块、作者提示、确认开关、目标变量和保存目标。
- 画布显示未连接节点、非法图、运行中、等待确认、完成、失败和已写回状态。
- 系统工作流只读；必须克隆为“我的工作流”后编辑，避免种子刷新覆盖作者修改。

### 3.4 执行和确认

- 图先编译为稳定拓扑顺序，再复用现有 `WorkflowRunner`、模型路由和
  `createWorkflowGenerationNode()`。
- 每个节点输出可编辑；下游只读取作者眼前已确认的版本。
- `saveTarget` 永远不会因为连线或运行完成自动写入；作者仍需点击节点上的保存动作。
- 世界观、故事核心、角色、大纲、伏笔等作品写回继续走既有 `adopt()`。
- 中止后不继续调度下游；失败节点可重试，尚未执行节点保持未运行。
- UI 明示节点调用次数和执行顺序；FLOW-1 不把多节点成本伪装成一次调用。

## 4. 第一阶段非范围

- 不支持循环、条件判断、并行模型调用、任意脚本节点或插件执行。
- 不新增图运行历史表，不跨会话保存模型中间产物。
- 不允许节点直接查询 IndexedDB、联网、启动本地 CLI 或绕过 Tool Registry。
- 不自动生成整套图；未来可由 Agent 提议图，但仍由作者确认后保存。
- 不在本阶段实现跑团、游戏状态、角色聊天记忆或 NPC 自动演进。
- 不追求复刻 ComfyUI 的图像模型、采样器、LoRA 或图像张量节点；StoryForge 的节点单位是
  Prompt、登记上下文、确定性检查和作者确认式作品采纳。

## 5. 与后续体系的关系

- `AGENT-1`：Agent 可以读取或建议 FLOW-1 图，动态任务仍使用同一 `GenerationNode`。
- `SIM-1`：未来模拟动作可成为受策略约束的节点类型，但运行时状态必须与创作 Canon 分层。
- `TTRPG-1`：可复用图来编排“读取战役状态 → 掷骰 → 规则判定 → GM 叙事 → 候选状态变更”。
- `CHATGAME-1`：可复用图来编排“角色记忆召回 → 行动判定 → 角色回复 → 场景状态候选”。
- 两个互动体系都不能把运行时事件自动写回作者原稿。

## 6. 第一阶段验证

### 纯逻辑与数据反例

- 旧线性工作流能无损生成兼容图并保持原执行顺序。
- 分叉、汇合得到稳定拓扑顺序；多入边只注入目标声明的变量。
- 悬空节点、悬空边、自环、重复边、环路和空端口全部阻断。
- 保存、刷新、克隆、工作流 JSON 导出导入保持节点位置和连线。
- 系统种子刷新不覆盖用户克隆图；不新增 DB 表和 schema 版本。

### 执行与写回

- 节点仍经 `GenerationNode` 调用，运行阶段不会自动写作品数据。
- 作者编辑输出后，下游读取编辑值而非原始模型值。
- 作者未确认时不能推进要求确认的下游。
- 点击保存后才经既有 `adopt()` 写回；失败或过期候选零写入。

### 真实产品验收

- 在隔离项目克隆系统工作流，拖动节点并建立分叉/汇合连接。
- 保存刷新后图不丢失，运行顺序和数据流可见。
- 使用真实 Agnes 完成至少两节点流程，编辑中间产物后确认下游确实读取编辑值。
- 拒绝候选和中止运行不写作品；测试工作流和隔离项目完整清理。
- 定向测试、完整 `npm run ci` 与 Chromium `npm run ci:e2e` 全绿。

## 7. 完成定义

第一阶段完成不是“画出几张卡片”，而是：

1. 真实用户能在画布创建、连线、保存、刷新并运行一个 DAG。
2. 图执行编译到现有 `GenerationNode`，没有第二个模型或写回入口。
3. 作者确认和确定性 gate 仍是作品写入前的硬边界。
4. 旧工作流无损兼容，数据生命周期和工作流 JSON 往返有反例。
5. 完整 CI、浏览器 E2E 和真实 Agnes 隔离项目验收通过。

## 8. 第一阶段交付证据

- `PromptWorkflow.graph` 已作为可选 v1 DAG 与现有步骤同行保存；旧工作流继续以内存兼容图
  保持原线性语义，不新增表、不升 schema。
- `src/lib/workflow/graph.ts` 提供纯代码图校验、稳定拓扑编译、分叉/汇合输入收集和变量归组；
  悬空节点/边、自环、重复边、非法变量和环路都会在保存、导入和执行前阻断。
- 工作区新增“节点模式”入口；用户可克隆系统配方，在画布拖动、连线、缩放、编辑端口和
  节点参数，并查看运行状态图。系统配方仍只读，作者工作流可安全删除。
- 执行仍经 `WorkflowRunner → createWorkflowGenerationNode() → GenerationNode`；显式图
  只向目标注入声明入边，较早节点重试或编辑会作废全部后序候选，作品只在作者点击既有保存
  动作后经 `adopt()` 写回。
- `R-FLOW1-*` 与既有 `R-WF-*` / `R-PIPELINE3-*` 覆盖兼容、反例、绑定输入、持久化、
  导入导出和 UI；Chromium 覆盖克隆、分支连线、保存刷新及清理。
- 真实 StoryForge 项目使用 Agnes 完成两节点确认链：作者编辑首节点候选后，下游输出包含
  编辑标记；全过程未点击作品保存，项目内容零主动写回，临时全局工作流已删除。

## 9. FLOW-2 当前独立实现（2026-07-26）

本节取代上面 FLOW-1 的产品完成结论；上文只保留为错误方案与可复用技术证据。

- 工作区“节点模式”现在加载 `NodeModeWorkspace`，与提示词管理中的
  `PromptWorkflowsPanel/WorkflowRunner` 完全分离。
- DB v47 新增项目级 `nodeFlows/nodeRuns`：前者保存自由图和动态端口，后者冻结每个节点
  的实际入参、来源纳入/省略/裁剪、Token 估算、输出、错误、gate 和采纳状态。
- 作者可自由添加文本、项目元素、整理合并、自由创作、内容校验和内容输出六类节点；
  支持分叉/汇合、类型端口、逐输入预算、全图运行和运行到任意节点的祖先闭包。
- 项目元素只通过 `CONTEXT_SOURCES → assembleContext()`；AI 节点只通过共享 `chat()`，
  分类为 `node.creation`；运行和连线不会产生 Canon 写入。
- 世界来源与新增角色是第一批明确确认目标。作者编辑输出并点击“确认采纳到项目”后，
  才经 `FIELD_REGISTRY / AdoptionSchema → adopt()` 写回；重复角色、非法角色 JSON、
  空内容、长度和 gate 失败均阻断。
- 图草稿会自动保存，即使尚未接完必需端口；运行前才执行完整图校验。刷新恢复、项目
  JSON 往返、世界/项目删除和节点图运行级联均由 `PROJECT_TABLES` 管理。
- `R-FLOW2-free-node-mode` 已覆盖路径校验、局部拓扑、输入输出持久化、作者编辑、显式
  采纳与删除级联。RAG-1 的记录/字段级可见选择器、稳定资料键、权重/预算和真实召回已由
  `RAG-VISIBLE-LIBRARY.md` 收口；条件、并行、模板、脏下游和 Agent 生成图仍属后续增强，
  不以当前来源分类筛选冒充。
- 真实浏览器隔离项目完成“自由文本 → 内容输出”连线与运行，运行记录公开 22 tokens 的
  实际输入和完整输出；刷新后图、连线及 completed 记录恢复。同期真实 Agnes 经主 Agent
  完成一个幕后世界来源任务并返回可编辑候选，作者拒绝后 Canon 零写入；隔离项目已清理。
