# AGENT-1 / 27.2b · 整理本章 Agent

> 状态：Phase 27.2b 首个后台 Agent 已完成（2026-07-27）

## 1. 产品边界

“整理本章”是章节编辑器中的一个手动后台 Agent。作者保存正文后触发一次分析，Agent
只生成可见候选，不直接修改正文、Canon 或其它业务表。作者可逐项取消，再明确确认写回。

首版一次模型调用完成六类结构化抽取：

1. 已登记角色的状态变化；
2. 带逐字证据的受控事实；
3. 角色物品获得/消耗；
4. 故事进程大事；
5. 已登记角色之间的新关系；
6. 已登记伏笔的埋设、呼应或回收推进。

它不是新的平行 AI 系统：解析继续复用状态、事实、物品、年表、关系适配器；写回继续走
`adopt()`、事实账本和现有状态/关系同步入口。

## 2. 为什么采用一次综合调用

旧界面把状态、事实、物品、年表、关系拆成多处按钮，同一章会被重复发送给模型。
整理本章把共同正文和登记清单只发送一次，再把返回的六个分区交给既有解析器校验。
这既保留项目级上下文，也避免五六次重复输入。调用仍受 Agent 团队预算预检约束；
上下文不足时在请求前停止，禁止静默裁剪。

每个候选都必须带正文逐字证据。证据不能在当前标准化正文中逐字找到的条目直接丢弃；
角色、关系端点、伏笔 ID、事实谓词和枚举值还要经过现有确定性注册表校验。

## 3. 可恢复数据方案

不新增业务表。每次整理使用已有 `agentConversations + agentEvents` 创作过程层保存：

- 独立归档 conversation 表示一次整理运行，不会混入主 Agent 的活动对话；
- candidate event 保存版本化候选、正文 hash、世界范围、预算证据和各域状态；
- confirmation event 追加保存作者实际选择、写入数量和失败信息；
- 刷新后按项目/章节读取最新 candidate，未确认结果可继续审核；
- 两张表已由 `PROJECT_TABLES` 管理导入、导出和项目删除。

正式业务表只保存作者确认后的结果。候选不是 Canon，也不会进入生成上下文。

## 4. 写回和过期保护

- 打开候选和确认写回前都重新计算章节标准化正文 hash；不一致即标为 stale，必须重跑。
- 状态：复用 `stateCards` adoption。
- 事实：只写 `temporalFacts.status=candidate`，仍需在事实库二次确认才成为 Canon。
- 物品、故事年表：作者确认后按 `chapterId` 通过登记的 replace scope 替换本章旧提取结果。
- 关系：经 `characterRelations` 的字段/集合登记写入，再同步角色文字关系字段。
- 伏笔：只允许单向推进；确认时若当前状态已变化则跳过，禁止旧候选覆盖新状态。
- 各域隔离记账；一个域失败不伪装整批成功，失败项保留以便复核。

## 5. 完成判据

- 章节工具栏只有一个“整理本章”主入口，旧状态/事实按钮收口；
- 一次模型调用、预算证据可见、可停止；
- 六类候选均可见、可逐项取消、刷新可恢复；
- 正文变化、跨项目角色/伏笔、伪造引文、重复关系、伏笔倒退均有反例测试；
- 确认前业务表零写入，确认后只写作者选中项；
- 定向测试、架构检查、完整 CI、浏览器流程和真实 Agnes 项目验证全部通过。
